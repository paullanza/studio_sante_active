# Studio Santé Active

Internal staff app for Studio Santé Active. It mirrors clients, contracts and services from the **Fliip** gym-management API, and lets staff log training sessions and consultations against a client's service. Admins confirm those records and adjust service usage. The interface is in French.

## What it does

- **Fliip sync:** clients (`FliipUser`), contracts and services are copied from the Fliip API into the local database. Fliip stays the source of truth, so local edits to those records are overwritten by the next sync.
- **Sessions and consultations:** staff record attendance against a client's service. Whether a session counts as paid or free is worked out from the service's allowance.
- **Admin tools:** service allowances, unconfirmed-record review and bulk confirmation, usage adjustments (with a CSV preview-and-commit flow) and CSV export.
- **Accounts:** roles are `employee`, `manager`, `admin` and `super_admin`. New staff sign up with a one-time code generated by a manager or admin.

## Stack

Rails 8.1, Ruby (version in `.ruby-version`), PostgreSQL, Devise, Hotwire (Turbo and Stimulus through importmap, so there is no Node or npm build step), Bootstrap 5 compiled by `dartsass-rails` and served by Propshaft, simple_form, pg_search and Pagy.

## Getting started

You need Ruby (the version in `.ruby-version`) and a running PostgreSQL where your user can create databases. The schema enables the `unaccent` extension.

```bash
git clone git@github.com:paullanza/studio_sante_active.git
cd studio_sante_active
bin/setup            # installs gems, creates and loads the development and test databases
```

Create a `.env` file in the project root (it is gitignored and loaded by `dotenv-rails`):

```
FLIIP_API_KEY=...
MAPBOX_API_KEY=pk....
```

| Variable | Needed for |
|---|---|
| `FLIIP_API_KEY` | The Fliip sync. The API client raises if it is missing. |
| `MAPBOX_API_KEY` | The address autocomplete on the sign-up and profile forms. Address is a required field, so without this key nobody can sign up or save a profile. Use a public `pk.` token with the Search Box API enabled. If you restrict it by URL, allow `http://localhost:3000` as well as the production domain. |

There are no seeds, so a fresh database has no users and sign-up needs a code. Create the first admin from the console:

```ruby
# bin/rails console
code = SignupCode.create!
User.create!(
  first_name: "Ada", last_name: "Admin", email: "ada@example.com", password: "choose-a-password",
  phone: "5145550100", address: "1 Main St, Montréal, QC", birthday: Date.new(1990, 1, 1),
  signup_code_token: code.code, role: :admin
)
```

Then start the app:

```bash
bin/dev              # Rails server on :3000 plus the Sass watcher (Procfile.dev)
```

Use `bin/dev` rather than `bin/rails server`: the stylesheet is compiled by `dartsass-rails` into `app/assets/builds/` (gitignored), and only `bin/dev` recompiles it when you edit a `.scss` file. Sign in at `http://localhost:3000`, then import clients with the import button on the admin dashboard (or `bin/rails fliip:sync`).

## Fliip sync

`bin/rails fliip:sync` does a full sync of users, contracts and services and exits non-zero on failure, so it is suitable for a scheduled job. Admins and managers can also trigger a full import from their dashboard, and the booking page has a button that imports only new clients.

## Tests and checks

```bash
bundle exec rspec        # specs (the Fliip API is stubbed; it is never called)
bin/rubocop              # style (rubocop-rails-omakase; existing offenses are listed in .rubocop_todo.yml)
bin/brakeman             # security scan of the code
bin/bundler-audit        # known-vulnerable gems
bin/importmap audit      # known-vulnerable JavaScript packages
```

CI (`.github/workflows/ci.yml`) runs all of those on every pull request and on pushes to `main`, with the specs running on Postgres 16 (the production major version). It also runs a production boot check: it installs production gems only, compiles assets twice (the second time on top of the existing manifest, like a cached deploy), then boots the app. The two dependency audits (bundler-audit and `bin/importmap audit`) also run every Monday, so a newly published advisory shows up without waiting for a pull request, and CI can be started by hand from the Actions tab.

## JavaScript packages

Packages are vendored into `vendor/javascript` and pinned in `config/importmap.rb`; nothing loads from a CDN. Add one with `bin/importmap pin <package>`. Afterwards check that no downloaded file name contains `#` and that none has relative imports (`from"./x.js"`): either one makes Rails drop the pin or breaks the module in the browser, and the specs will not notice. Confirm in a browser.

## Data model

| Model | Purpose |
|---|---|
| `User` | Staff accounts (Devise) with a role. |
| `SignupCode` | One-time code that lets a new staff member sign up. |
| `FliipUser` | A client or Fliip staff record, copied from Fliip. |
| `FliipContract` | A client's membership contract, copied from Fliip. |
| `FliipService` | A service a client purchased, copied from Fliip. |
| `ServiceDefinition` | Local allowance (paid and free sessions) per Fliip service type. |
| `Session` | A booked training session for a client and a service. |
| `Consultation` | A consultation, optionally linked to a client and a service. |
| `ServiceUsageAdjustment` | A manual correction to a service's usage or bonus sessions. |

## Deployment

The app runs on Render and deploys from `main`. The services are configured in the Render dashboard, not in the repository (there is no `render.yaml`).

- **Web service** (Ruby runtime): build command `./bin/render-build.sh`, start command `bundle exec rails server`. The build installs gems, compiles assets, runs migrations and runs `db:seed`, so seeds must stay idempotent. The app exposes `/up` as a health endpoint.
- **Cron job `fliip-user-sync`:** the same build command, running `bundle exec rake fliip:sync`.

Set these on the web service: `RAILS_MASTER_KEY`, `DATABASE_URL`, `WEB_CONCURRENCY`, `FLIIP_API_KEY` and `MAPBOX_API_KEY`. The cron job boots the whole app in production, so it needs the same environment, in particular `DATABASE_URL`, `RAILS_MASTER_KEY` and `FLIIP_API_KEY`.
